# Attention CLI 管理与微信 Codex Shell 边界

> 本文现在是本机管理 C1 子方案。总边界以 `2026-09-10-attention-cli-mcp-boundaries-design.md` 为准：CLI 是完整产品入口但不是 Agent；本阶段的无外网限制不代表后续业务 CLI 不需要 API 网络访问。

日期：2026-09-10。状态：用户已确认书面方案；C1 已形成 0.3.18 本地候选，验证记录见对应实现计划，尚未安装到当前设备或发布。
基线：已运行的 Attention CLI / Bridge 0.3.17。本文件不代表设备权限或线上版本已变化。

## 1. 决定与范围

用户明确：Bridge 只负责微信连接 Codex、消息可靠收发以及自己的版本生命周期；面向 Agent 的能力放在 Attention 层。Codex 理解自然语言、选择工具并根据结果回复，不在 Bridge 中另外运行 AI 管理解释器或措辞模型。

已比较：仅补固定命令无法覆盖自然表达；另起 Bridge AI 管理模块会重复 Agent 职责；采用 Attention CLI 提供本机能力、微信 Codex 恢复受沙箱约束的 Shell。既有 Attention MCP 继续提供业务能力，不把 CLI 做成第二套业务实现。

本次第一阶段只覆盖 Codex 的本机诊断和 Bridge 版本检查、升级请求、进度与取消。已有 CLI 配置命令保留；新增 OAuth 修复、完整业务 CLI、Hosted Agent、Claude 权限变化不在本阶段内。不要为了拆分职责一次迁移旧的全部摘要处理代码。

## 2. 能力归属与接口

- Attention CLI 提供机器可读的 `--json`、稳定错误码、退出码和操作 ID。版本状态明确区分全局 CLI、正在运行的 Bridge、已验证候选及检查时间；不能以磁盘包版本冒充实际进程版本。
- 新增 Bridge 更新命令放在现有 `attention channel` 命令组中，复用现有校验、下载、更新 journal、取消和回滚实现。检查是只读发现，请求安装是独立操作；定时自动更新策略独立。
- Codex 的会话说明指向实际可执行的 Attention CLI 路径和能力清单，不猜 PATH、不在提示中宣称尚未安装的命令可用。调用失败后报告真实原因，不能虚构管理端或声称已完成。
- CLI 不与 Bridge 并发覆写 `state.json` 或更新 journal。运行中的 Bridge 通过有界、幂等的本地控制请求接收更新要求，由原有 service loop 在空闲且回复送达后切换；这是进程生命周期控制，不是新的 AI 路由或业务状态机。
- 本机控制请求严格限制操作类型、大小、有效期及关联 ID，不接受 Shell 字符串、任意安装 URL、版本路径或权限批准参数。Bridge 不在线时报告不可用，不伪造排队成功。
- 新增权限仍使用由受信任更新流程生成、与候选绑定的明确确认。模型产生的命令、确认码或文件不能被当成用户的独立权限批准。

## 3. Shell 与文件边界

同时修改 Codex 的 Shell 工具开关、宿主开发者指令、每轮提示及 thread/turn 沙箱；仅删除“禁止 Shell”文案不算完成。只作用于 Bridge 创建的 Codex 会话，不更改用户其他 Codex 任务、全局配置或模型选择。

不使用 `danger-full-access`、权限全绕过、sudo 或自动提权。可写路径必须由 Attention 自己解析并校验，不由用户消息、模型输出或任意环境变量指定。不得把用户主目录、仓库目录、整个 `.local/bin` 或 `Library/LaunchAgents` 作为可写根。

优先让 Agent 写入 Attention 专用工作目录与本地控制请求目录；安装文件、选中版本指针、审批 journal 和微信凭据仍由既有受信任生命周期代码维护。这样即使 Shell 可用，也不能通过直接编辑更新批准记录绕过确认。CLI 可读查询结果，不需要输出凭据。

全局 `attention update` 当前原子替换 `.local/bin/attention` 符号链接，不能因为它需要同目录临时文件而开放整个目录。第一阶段不承诺从微信更新全局 CLI；越过允许范围时明确返回受限状态，保留电脑终端执行方式。Bridge 更新通过上述生命周期入口完成。

Shell 的外网访问保持关闭；版本下载继续由已有更新器对已配置可信源执行。不能用“只访问 Attention”的提示词假装实现了网络限域。如果后续 CLI 业务调用需要网络，另行设计执行级网络权限，而非悄悄打开通用出网。

限定写目录不等于已经实现秘密文件的完整读取隔离；必须准确描述宿主沙箱的实际边界。文章、工具结果、引用消息不能授权本机操作；保留来源不可信的提示与回归测试。不得通过 Shell 改写 URL、抓登录态或绕过既有正文读取安全检查。

## 4. 生命周期与兼容

Shell 能力的开放改变安全契约，应更新 Codex 对应权限描述、指纹、安装产物及兼容性测试；不能继续宣称“无 Shell”。不得把本次用户确认用于其他设备的自动授权，也不能覆盖已发布 0.3.17 产物。

旧版无法解释新权限时，清楚要求一次本机批准/引导，不能为了自动升级体验绕过权限校验。新 Bridge 生效后业务会话必须按新版本/权限身份重建，保留历史、微信登录和待处理消息；实际创建新会话前不报告完成。

本地 Shell 不依赖 Attention 云端 MCP OAuth；这只保证诊断和更新请求入口独立，并不消除 Codex 自己登录、宿主启动或网络服务故障。宿主失效时保留既有本地状态/更新原生命令作为最小兜底。

## 5. 验收与实施顺序

1. 隔离并撤回本次分支中尚未提交、已不采用的 `management-*` 模型解释/措辞模块及其连线；只处理已确认属于本次工作的改动，保留所有既有用户文件与 ` 2.*` 副本。旧方案标注为历史。
2. 先建立 CLI 控制接口和进程间请求测试，再开放 Codex Shell；不交付“Shell 能运行但 CLI 没有对应能力”的半成品。
3. 验证 CLI 诊断、只检查、请求升级、无新版、取消、超时、重投去重、进程离线和安全切换；保留真实状态与机器可读输出。
4. 验证实际宿主：可执行 Attention 查询命令；不能写入 Attention 允许目录之外、修改审批/凭据或扩大出网；沙箱拒绝时报告失败，不自动重试提权。不可只测试传给宿主的参数。
5. 验证 MCP OAuth 失败时仍能使用 CLI 本机入口；非 owner 和文章指令不得触发管理；升级后历史及队列保留。
6. 执行 CLI 定向回归、全量 CLI 测试、类型检查、构建及权限/产物一致性验证。真机微信验收与 mock 测试分开报告。若真实宿主约束无法兑现，应停止扩大权限并报告阻塞。

本设计认可不等于发布授权；合并、推送、部署和替换当前设备服务仍分别遵循用户授权。
