# Attention Bridge 与 Hosted Agent 任务对话设计

日期：2026-09-05

状态：两端统一体验方向已确认；以下具体合同为讨论稿，尚未实现

## 1. 共同目标与现状

Bridge 与 Hosted 都应允许用户围绕同一任务连续对话：发链接、询问进度、要求补摘要、重试、取消，并在执行中断后继续处理。正常回复由 AI 根据真实任务状态组织；任务调度、授权和结果不能以模型文字为依据。

本文件补充 [Bridge 摘要重试设计](./2026-09-04-attention-summary-retry-experience-design.md)、[MCP 恢复设计](./2026-09-03-attention-channel-mcp-recovery-design.md) 与 [Hosted 设计](./2026-08-25-cloud-agent-executable-readiness-design.md) 的任务对话合同。它不代表 Hosted 已交付，也不改变现有第一版范围、安装权限或凭据保存位置。

Hosted 的完整架构、授权、渠道与分期方案见 [Hosted Agent 完整设计](./2026-09-05-attention-hosted-agent-complete-design.md)。本文件继续作为两端的共同体验与契约测试依据，不把云端实现依赖引入本地 Bridge。

2026-09-05 对当前代码的核对结果：

| 能力 | Bridge 0.3.15 | Hosted |
| --- | --- | --- |
| 收藏结果自然回复 | 已实现，保留输出检查和安全兜底 | 旧稿的固定模板要求由本稿调整 |
| 摘要有限自动重试 | 已实现，本地持久化，2/10/30 分钟退避 | 需要持久化调度，尚未实现 |
| 精确的逐任务追问 | Prompt 只有重试数量、最近时间；不能证明某条任务正在执行 | 需要加入任务关联与查询 |

| 对话取消任务 | 尚无明确的任务取消命令；内部移除重试项不等于用户取消能力 | 旧稿有取消规则，需支持明确目标及歧义处理 |
| 升级后的会话 | 用户消息路径校验版本；自动摘要重试路径只校验宿主类型 | 任务恢复与模型会话恢复需分别定义 |

## 2. 用户对话合同

| 用户意图 | 两端应执行的行为 |
| --- | --- |
| 发链接收藏 | 建立明确任务，沿用现有账号、候选选择和 Core 收藏规则；Core 接受后即保留收藏 |
| “在做了吗”“怎么样了” | 查询目标任务的最新状态；单纯查询不触发新的摘要尝试 |
| “补一下摘要”“再试一下” | 定位目标，检查当前 Core 状态与执行权；已完成则说明结果，未完成则安排一次人工尝试 |
| “取消”“先别做了” | 定位目标并取消待执行工作；运行中的任务请求停止，已保存的收藏和摘要仍保留 |
| “刚才那篇”“上一条” | 通过持久化任务关联定位；多个合理目标时简短澄清，不能靠模型猜 Collection ID |
| 明确要求重新连接 | 调用受控的依赖恢复操作；恢复后继续原任务，不重新创建收藏 |
| 与任务无关的短对话 | 可自然回应；不得因此创建任务、修改收藏或消耗摘要重试次数 |

任务定位优先使用明确引用的原消息或任务，其次使用最近已明确的任务焦点。没有明确引用但只有一个相关任务时可自动定位；多个目标且焦点不明确时必须澄清。任务焦点在重启后仍应可用；用户主动清空会话时清除焦点，但不隐式取消持久化任务。

无修饰的“重试”在目标任务明确时表示重试该任务；任务被依赖阻塞时先恢复依赖再继续。没有相关任务且连接故障明确时表示恢复连接；两者都不明确时澄清。保留 `/retry` 等现有显式诊断命令的兼容行为，帮助说明应区分它和业务任务重试。

## 3. 真实状态先于回复

必须分别保存收藏结果、任务执行状态和通知投递状态。`summary_status=pending` 只能说明内容没有摘要，不能推导任务存在、正在运行或已安排重试。

建议的逻辑状态如下；这是合同草案，不要求两端立即采用相同数据库结构：

- `queued`：已持久化、等待执行权。
- `running`：执行器已开始一次尝试，且仍持有有效执行权。
- `retry_scheduled`：本次未完成，已持久化下一次尝试时间。
- `waiting_dependency`：正在等待有界的依赖恢复；不消耗内容重试次数。
- `needs_action`：需要用户重新授权、登录或选择目标，不能继续自动执行。
- `paused`：本轮自动尝试耗尽或恢复预算耗尽，用户可以再次触发。
- `completed`：Core 返回完成或可复用结果。
- `cancelled`：目标工作已停止；已经产生的 Core 结果不自动删除。
- `failed`：已得到明确终态原因，不再自动重试。

Bridge 的 `running` 依据本地执行锁和检查点，Hosted 依据任务租约及其有效代次。重启后先核对 Core 已产生的结果，再恢复未完成工作，不能仅凭旧 `running` 标记声称仍在执行。

运行时向对话层提供最小逐任务快照：受当前账号和会话约束的任务引用、来源消息关联、收藏引用、执行状态、尝试次数、下一次时间、稳定失败类别和允许操作。完成、取消和暂停任务也需要有界保留结果，避免移出活动队列后无法回答“刚才怎么样了”。保留期限与数量在实施计划中明确，不默认长期保存原文或完整聊天记录。

## 4. AI 表达与受控动作

AI 可以理解用户表达、提出目标与操作，并根据已经提交的任务快照自然回复。运行时必须再次验证目标属于当前账号、动作合法、权限有效、任务状态未被其他执行器改变，然后执行并返回结构化结果。

只有任务调度持久化成功后才可确认“已安排”；只有执行实际开始才可说“正在处理”；只有 Core 确认结果才可说“已完成”。回复生成之前重新取得动作后的快照，不能用动作前状态作成功承诺。文字校验不能代替执行事实校验。

正常的任务状态、恢复说明、暂停与结果通知都使用这一表达方式。模型不可用、文本为空、事实不受支持或输出不安全时，才使用基于真实状态的简短兜底。兜底不得承诺未入队的重试或要求用户重启一个已经在恢复的服务。

既有隐私与工具边界继续适用。任务引用可在运行时内部用于定位，向用户展示时使用短序号或明确的会话关联；本轮不扩大原文、摘要、认证信息或内部标识的回显范围。

## 5. 执行、恢复与通知

1. 可恢复的摘要失败沿用 2/10/30 分钟、三次自动尝试的基线；每个间隔从前一次失败结束后计算。人工触发不消耗自动次数，也不延后已有计划。
2. 网络、模型、MCP/Core 或执行器故障使用独立恢复预算；不消耗内容重试次数，但必须有尝试/时间上限，耗尽后明确暂停，避免无限恢复。不可刷新的授权进入 `needs_action`。
3. 用户问进度时能及时查到任务快照；取消能登记停止请求。控制消息处理不能一直排在长时间网页读取后面，实际业务尝试仍遵守串行规则。
4. 取消等待任务立即生效；取消运行任务先记录请求，再在受控停止点确认。取消与 Core 提交竞争时，以已确认的提交结果回复，不声称已撤回保存。
5. 同一执行范围内，人工与自动重试共享执行权及幂等键。Core 已完成时复用结果。停止旧尝试后才能启动下一次，防止取消或升级后旧执行器继续写入。
6. 首次失败说明已安排的恢复；自动尝试的中间失败保持静默；成功、暂停或需要用户介入时主动通知。用户主动查询始终可以得到当前状态。
7. 任务结果落定与通知发送分别持久化。发送失败只重试通知，不重新生成摘要或收藏；同一结果事件在同一投递目标去重，用户主动查询的答复不算重复主动通知。
8. 通知文字生成失败不能导致最终结果事件丢失；使用兜底进入 outbox。渠道不可用或平台不允许发送时保留真实结果与投递状态，不假称已送达。
9. 重启或升级后，所有 Agent 调用入口均校验会话与运行版本的兼容性，包括用户消息、自动尝试与 AI 通知生成。模型会话重建不删除任务、不重复计次、不丢失任务焦点。

## 6. Bridge 与 Hosted 的执行边界

Bridge 的任务状态、凭据与执行留在本机，电脑关闭时无法继续执行；下次启动后恢复到期任务。Hosted 在服务端持久化任务并由云端执行器领取，在用户电脑关闭时仍可运行，但仍受服务健康、账号权限和渠道条件约束。

两端共享合同、错误分类、Core 结果语义和验收场景；持久化与执行器可分别实现。Hosted 的新任务按账号串行，状态查询和取消请求不需要等待同账号的网页任务结束。Pi 或其他 agent loop 的选型保持待验证，不把它当成任务持久化层。

同一收藏同时出现在多台 Bridge 和 Hosted 时，Core 结果幂等只能防止重复提交，不能自动防止重复读取、模型花费或多端通知。首个双端试点采用明确的任务执行归属，不隐式转移任务；跨设备接管、共享执行租约和全局通知归属另作实现合同。在这些合同落地前，不宣称两端无缝接力或全局只执行一次。

## 7. 下一步实施拆分与验收

Bridge 先补逐任务关联/结果保留、状态查询、任务重试分流和取消，再统一恢复及通知的事实快照。已有 0.3.15 摘要队列保留并迁移；自动任务入口的会话版本检查需要一并补齐。

Hosted 用同一组任务对话用例验证独立执行器；先用 Fake Channel 证明任务生命周期，再按原设计验证真实微信客服渠道。真实渠道门槛仍适用于 wxkf 接入，不妨碍离线合同和 Fake Channel 验证。浏览器登录态托管、模型选型、渠道发送规则等在对应实施阶段单独核实。

两端共用的验收场景：

- 同一链接从收藏、摘要失败、安排重试到成功通知，回复均可追溯到真实结果。
- 单任务的“在做了吗”“再试一下”“取消”正确定位；多任务歧义不误操作。
- 无任务的 `pending` 不声称后台运行；纯状态询问不触发工作。
- 长任务期间状态查询与取消请求可被接收和确认。
- 人工/自动重试竞争、依赖恢复、结果提交与取消竞争不会重复写入。
- 模型、执行器、Bridge/Hosted 服务在关键持久化点中断，任务与结果通知可恢复。
- 升级后第一项工作是自动重试时，同样重建不兼容会话；恢复任务焦点后仍能继续对话。
- 多种 AI 表达都可接受；无根据的“正在做”“已重试”“已完成”不能作为成功证据。
- 通知失败、重复事件及生成文案失败不会导致结果丢失或重新执行任务。
- Bridge 停机和 Hosted 服务故障分别准确呈现，不承诺不具备的后台能力。

当前仅完成设计对齐；运行代码、CLI 版本与线上部署尚未包含本文件新增能力。
