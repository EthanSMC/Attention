# Bridge 微信升级确认闭环：设计与实施拆分

日期：2026-09-10  
状态：设计已批准，0.3.17 实现与本地受控测试已完成；用户进一步授权“改代码然后合并部署”。当前设备新增权限与首次引导仍需单独确认。
基线：main `94b7b3a`，公开 CLI 0.3.16。实现时重新核对最新分支和版本，不覆盖任何既有未提交文件。

## 1. 问题和目标

当前 Bridge 启动及运行中每小时检查更新。权限摘要变化或跨主版本时，
`bridgeUpdateDecision` 返回 `consent_required`，`checkAndStageBridgeUpdate` 停止下载，
`channel-command` 只写后台日志。没有微信升级通知、确认入口或重启后的结果回执。

9 月 10 日真实检查：全局 CLI 0.3.14、运行 Bridge 0.3.15、远端 0.3.16。
Bridge 已发现更新，但新增 `attention_read_collection_source` 令其等待确认。
旧业务会话仍使用旧读取能力。此前部署验收不等于设备升级，更不等于收藏摘要验收。

目标：在同一已绑定的微信对话中完成“发现 → 解释变化 → 明确确认 → 校验下载 →
安全重启 → 会话重建 → 回报结果”。控制流程不依赖模型、MCP OAuth 或 Hosted Agent。

不在本方案内：修复公众号 `unsafe_source` 的根因、启用尚未验收的浏览器读取后端、
批量补写历史摘要、修改 OAuth 授权范围、清理缓存和无关代码重构。发布部署按用户后续明确授权执行。
本方案允许之后真实测试已有收藏，但不得把升级完成描述为摘要已经写入。

## 2. 方案选择

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| Bridge 本地控制命令（推荐） | 微信内闭环；模型/MCP 故障时仍可确认 | 需要耐久授权、重启和通知状态 |
| 微信提供网页审批链接 | 易展示复杂权限差异 | 新增页面及鉴权、设备与审批绑定，首版范围更大 |
| 微信只提醒，终端确认 | 改动较少 | 仍需切换设备和终端，不能满足完整微信闭环 |

采用第一种。首版只对客户端能完整解释的、受限 Attention 云工具清单变更提供微信确认。
跨主版本、未知权限类别、local deny/write、native network 或 Runtime OAuth 范围变化，
仍说明原因并要求电脑端单独审查；不能用“同意”一次批准未来所有权限。

用户于本轮明确“通过对话升级就行”：正常支持范围内只用微信对话，不新增审批网页，
不要求常规升级跳转本机终端。超出可解释权限范围的升级在微信明确拒绝并说明边界，
不为了维持无感体验而默认批准。首次旧版本引导是第 7 节明确的迁移例外。

## 3. 微信交互

### 3.1 通知与指令

兼容 patch/minor 更新仍自动完成，不新增日常成功刷屏。需要人工操作时通知已固定的 owner。
同一候选身份只主动通知一次；每小时检查不得重复发消息。没有有效 iLink 登录、owner 或
context token 时保留待通知事件，等该 owner 再次发消息后投递，不冒充已通知。

推荐提示示例（版本和确认码仅为示意）：

> 发现 Bridge 新版本 0.3.17，当前为 0.3.16。本次新增：读取你已收藏的公开原文。
> 不开放 Shell、本地文件或其他 MCP。升级会短暂重连，保留微信登录和待处理消息。
> 确认请回复「确认升级 0.3.17 K7M2Q9」，10 分钟内有效；也可以回复「稍后升级」。

首版命令：

- `检查更新`：限频检查远端，展示运行版/候选版及必要操作；不构成授权。
- `升级状态`：只读取本地状态，不触发下载、确认、重启或摘要重试。
- `确认升级 <版本> <确认码>`：仅批准当前展示过且未过期的候选。
- `稍后升级`：撤销未使用的 offer，不影响兼容自动更新；同一版本不再主动提醒。
- `取消升级`：在原子切换前撤销本次操作；下载取消须等待清理结束。切换提交后明确已进入
  重启阶段，不宣称已取消，亦不隐式启动一次回滚。
- 普通 `状态`、`帮助` 中补充更新状态及上述入口；泛化的 `重试` 保留原有 MCP 恢复含义。

确认过期后不接受旧口令；用户主动发送 `检查更新` 可获得新的 offer。
升级因网络或候选校验失败后旧版本继续服务。首版不无限自动重试已获授权的安装；
用户 `检查更新` 获取新状态并重新确认。兼容后台检查仍每小时执行。

更新控制文案由可信事实和本地文案生成，不依赖 AI。业务聊天继续由 AI 组织。
这些是控制/授权信息，不将普通聊天改为统一固定回复，也不让远端发布说明决定授权文字。

### 3.2 授权来源

只接受已经 pin 的 owner、当前真实 iLink 入站、单个顶层纯文本 item 的完整命令。
不复用会把引用标题、转发和语音拼入正文的 `extractText` 来判定授权。
引用、转发、图片、语音转写、代码块、URL、历史回放、模型输出、其他 peer 都不得批准。
普通“好的”“同意”“为什么不能升级”“不要升级”均不批准。
确认处理不得首次建立 owner；尚未绑定时继续既有绑定流程。

确认码使用安全随机源生成，6 位大写字母/数字、10 分钟有效、每个 offer 最多 3 次失败。
它只用于将用户意图关联到 offer，不代替微信 owner 身份验证；不进入遥测或聊天历史回放。
确认前先检查过期、版本和 owner，再验证完整候选身份。重复 iLink 消息只消费一次。

## 4. 发布元数据与权限差异

现有 v2 manifest 只有权限 SHA，不能从摘要推导“新增了什么”。保持 v2 字段和旧 probe
输出不变，避免旧 CLI 的严格解析失败；新增同 origin 的固定路径只读侧车：
`/cli/permissions/<permission_profile_sha256>.json`。

生成脚本从实际 `ATTENTION_BRIDGE_PERMISSION_PROFILE` 产出侧车，使用严格已知 schema、
限定长度/深度/字段，按与现有 fingerprint 一致的序列化规则重建后校验 SHA。
权限说明只由已知工具 ID 的本地字典派生，不直接显示任意远端自然语言来获得授权。
缺失侧车、摘要不匹配、未知工具或无法完整解释的字段：仅提示需电脑端审查，不显示可批准口令。

offer 绑定以下完整身份，不只是版本：标准化 origin、manifest schema、版本、artifact path、
artifact SHA、权限 SHA、Node 要求、minimum-supported-version、当前运行版本/权限和 owner 指纹。
确认后重新获取 manifest：任意字段变化即失效，必须展示新 offer。相同版本替换字节也不放行。
候选必须高于当前运行版本；本功能不执行用户口令指定的任意版本或降级。

下载仍执行现有 HTTPS 同源、禁止重定向、大小、Node、SHA、候选身份 probe 和原子切换检查。
权限不同的候选在明确确认前不运行 probe。授权不是关闭安全校验的通行证。
现有 HTTPS + SHA 校验不应被文档称为“数字签名”；本方案不另造签名基础设施。

## 5. 本地架构和耐久状态

建议拆成小模块，避免继续堆叠 `channel-command.ts`：

- `bridge-update-offer.ts`：元数据、权限差异、候选身份、offer 校验，纯函数优先。
- `bridge-update-control.ts`：顶层入站命令、owner 校验、节流和授权消费。
- `bridge-update-journal.ts`：本次操作及跨重启结果的有版本原子日志。
- 现有 `bridge-updater.ts`：将发现与 stage 分开，复用原有安全下载/probe；确认只是显式能力输入，
  不修改 `bridgeUpdateDecision` 使权限变化自动通过。
- 现有 queue/outbox、managed launcher、会话身份检查负责可靠投递和实际进程切换。

持久化日志建议位于 `~/.attention/update/wechat-update.json`，目录 0700、文件 0600，
只存候选摘要、owner 指纹、期限、已消费入站引用、阶段、稳定错误码和通知事件。
不存 OAuth/iLink token、文章、摘要、任意命令或完整聊天。微信 context token 仍归既有 channel state。
保留有界终态事件（例如最近 8 次）；未投递的终态不得被清理。缺省字段可迁移，未知 schema 拒绝写入。

阶段：`offered → approved → downloading → waiting_safe_point → switching → started`，
另有 `deferred / expired / cancelled / failed / rolled_back`。`offered` 不是已经授权；
`approved` 不是已经安装；`started` 不是 MCP 或摘要已经成功。

以 operationId + 完整候选摘要关联 update state 与 journal。使用单写入者/互斥与身份条件检查，
在切换前持久化 switching 意图；崩溃后根据实际 current/pending/previous 对账，不盲目重跑下载或重启。
旧 updater 的 catch 分支目前会无条件还原 originalCurrent；实施时限定只能撤回本 operation
拥有的变化，不能覆盖并发发生的较新状态。

每个通知事件用稳定 ID 写入现有 outbox，先落盘再发送。崩溃重放复用 client_id；不承诺跨
iLink 外部系统的绝对 exactly-once。不要先标为“已通知”再执行可能失败的发送。

## 6. 调度、安全切换和回滚

### 6.1 OAuth 不得卡住控制面

更新命令在调用 Brain 之前处理，可越过被 MCP 阻塞的业务消息；业务消息之间仍保持 FIFO。
当前队列只取前 5 条，必须专门回归“第 6 条及之后的本地控制消息仍能被处理”，不能只添加命令词。
查找需有消息数量和单轮工作预算，不能无界扫描或让控制命令饿死业务。

发现/通知和受限下载可以在业务队列非空时执行，但不与活跃 Agent turn 并发修改 channel state。
网络任务必须可取消且有超时，由串行控制器提交结果；不得阻塞 iLink 长时间收发。

### 6.2 切换屏障

为了让被 OAuth 阻塞的队列仍可带着修复升级，本方案有意调整旧设计的“入站队列必须为空”规则：
切换要求 **无活跃业务 turn、无活跃摘要恢复、已停止接纳新业务执行、全部入站已持久化、
全部出站回执已确认发送且无在途发送**；已持久化但尚未执行的入站允许保留并由新版继续。
这不是在处理过程中强杀或把排队消息标为成功。若不能证明满足这些条件，只等待并解释当前原因。

微信确认触发的升级先持久化升级开始回执，正常投递后再进入最终切换；兼容自动更新不新增
开始/成功消息，只保留本地结果，失败需人工操作时才通知。已有出站仍须全部发送完成。
iLink 无法投递时不强行切换，保留操作并报告本地 waiting 状态；显式授权从确认起最多保留
30 分钟，超时撤销执行资格并要求重确认，不将此授权期限套用于无需确认的兼容自动更新。
每次实际切换前再验证候选未变化。用户批准后的正常入站消息继续耐久接收，但暂缓执行。

新旧版本的状态/队列格式必须可双向读取，才允许本地自动回滚。新 launcher 保留耐久结果；
新版启动或旧版回滚后，由运行中的 Bridge 对账并投递一次升级结果，不让 launcher 读取聊天 token。
不支持回滚兼容性的候选不得进入微信确认安装。

### 6.3 真实结果与能力状态

- 版本切换后先核对运行产物身份；旧业务 session 不再复用，保留历史和登录、队列、幂等记录。
- 同进程新配置完成 Runtime 初始化和真实账号探针；下一业务 turn 必须创建版本匹配的新 session。
- 新业务 session 实际创建前，只说“后续对话将重建”，不能把启动用的一次性账号探针称为
  业务会话已经重建；验收必须观察第一条真实业务消息的新 session 身份。
- MCP 可用时验证新工具清单；不可用时准确回报“Bridge 已升级，Attention 授权/连接仍需恢复”。
- OAuth 故障本身不回滚能正常聊天的 Bridge；Runtime 协议/隔离失败按既有健康门槛回滚。
- 启动失败/超时保留旧版，回滚结果经耐久日志投递，暂停同一失败候选的自动重装。
- 成功消息包含实际运行版及 MCP 分层状态；只有真实 enrichment 提交与状态复查成功才能说“摘要已补全”。

## 7. 第一次安装与版本策略

当前 0.3.15 不认识新微信命令，发布新版不会让它凭空获得确认能力。
第一轮需要用户在电脑端明确批准新权限后，通过公开 CLI 更新 + 后台服务安装路径升级一次，
同时刷新稳定 launcher。不能手改 fingerprint、consent_required 或 channel state 来伪造通过。

首个具备闭环能力的版本作为协议基线（以实施时空闲的下一个 patch 号为准）。
只有 running、candidate、rollback 三方支持结果日志和兼容状态格式时，后续微信内切换/回滚
才承诺通知闭环。第一次从 0.3.15 引导失败时，由本机安装程序报告，不承诺老版本能发新回执。

Bridge 更新不顺带覆盖全局 CLI：仍分别显示二者版本，避免“全局命令旧 = Bridge 未升级”的混淆。
实现及测试不包含推送、部署、用户服务重启或当前新增权限批准，这些交付步骤单独获得授权。
