# Attention 管理端用户权限界面与交互修复设计

**状态：** 待实施  
**日期：** 2026-09-03  
**基础设计：** `2026-08-27-attention-admin-user-entitlements-design.md`

## 目标

修复 `/admin/users` 的信息层级和权益操作反馈，使管理员能理解按钮何时可用、为什么不可用，并能完成真实的单用户权益变更。管理端继续是独立、不可从用户站点导航发现的服务端受保护入口。

## 已确认根因

当前每行操作按钮同时受三个条件控制：请求处理中、原因不足 3 个规范化字符、当前权益已满足或不支持该动作。原因初始为空，因此三个按钮首次渲染时全部禁用；页面仅在 textarea 占位符中说明 `3–500` 字，反馈区域为空，禁用样式又统一降低透明度并显示不可用光标。管理员只能看到一组类似失效的按钮，无法判断需要先填写原因。

现有组件测试只验证静态服务端标记、理由校验函数和确认框文案，没有驱动输入、动作选择和请求提交，因此没有覆盖这类交互理解问题。

## 信息架构

### 独立管理壳

新增管理端专用壳层，不把 `AccountSettingsShell` 改成通用组件，也不复用其中的用户站路由。管理壳只复用正式站已有的设计 token、账号身份表达、侧栏比例、选中态和响应式规则。

桌面端采用左侧身份与导航、右侧内容的两栏结构：

```text
┌──────────────────┬─────────────────────────────────────────┐
│ 管理员身份        │ 页面标题与说明                            │
│ 姓名              │                                         │
│ 邮箱 / @ID        │ 当前 Tab 的筛选、列表或审计记录            │
│ Admin             │                                         │
│                  │                                         │
│ 用户权限          │                                         │
│ 审计记录          │                                         │
└──────────────────┴─────────────────────────────────────────┘
```

身份区域为只读，不提供修改资料、进入用户账户页或返回用户站的链接。全站 `SiteHeader` 和移动端产品导航在 `/admin/*` 下继续隐藏。

移动端将身份区域放在内容顶部，导航变为可横向滚动的 Tab；表格保留横向滚动，不压缩账号、权益和操作内容到不可读宽度。

### 用户权限 Tab

保留现有邮箱、昵称、Attention ID 搜索，权益筛选和服务端分页。每行继续展示账号、注册时间、当前权益和单用户操作。

“查看审计”进入审计记录 Tab，并携带目标账号 ID。查询、权益筛选和页码在 Tab 切换或打开审计时尽量保留，返回用户权限时不丢失管理员的列表位置。

### 审计记录 Tab

首版继续使用现有的按用户审计查询，不新增全局审计接口。

- 从用户权限 Tab 进入时，直接展示所选用户最近 50 条权益记录。
- 直接打开审计记录 Tab 且未选择用户时，显示明确空状态，并提供返回用户权限选择账号的动作。
- 记录展示动作、前后权益、原因、操作者、时间、来源和请求 ID。
- 审计记录只读；不提供删除、编辑或批量操作。

## 权益操作交互

### 原因校验与提示

原因仍按 NFKC 规范化后去除首尾空白，长度必须为 3–500 个字符。textarea 下方提供持久、就地、可被辅助技术关联的状态提示：

- 空值：`先填写至少 3 个字符的变更原因。`
- 1–2 个字符：`还需填写 N 个字符，才能选择操作。`
- 合法：`原因已满足要求，请选择操作。`
- 超长：由 `maxLength=500` 阻止继续输入，服务端仍保留 500 字上限校验。

操作按钮使用 `aria-describedby` 关联提示。因理由不足而禁用与因当前权益不适用而禁用需要能被区分；当前权益不适用时提供具体说明，例如“当前已是 Member”或“仅 Filter 可撤销”。

### 动作与确认

保留三个现有动作及语义：

- 设为 Member：确保 Member 有效，并撤销当前 Filter grant。
- 设为 Filter：保留或补齐 Member，同时创建或恢复 Filter grant。
- 撤销 Filter：只撤销 Filter，保留 Member。

满足理由要求后，仅当前状态允许的按钮进入可用态。点击先打开明确确认对话框，重述目标账号、动作和规范化后的原因；只有“确认并执行”才发起 POST。请求处理中禁用对话框动作，避免重复提交。

成功后清空原因、关闭确认框、刷新服务端页面数据并显示成功反馈。失败时保留原因，显示安全、可操作的错误信息；网络结果不确定时提醒管理员先确认当前状态再重试。

## 数据流与安全边界

页面仍先读取会话，再调用 `requireAdminPrincipal`。所有 `/api/admin/*` 读写路由继续独立执行同样的服务端管理员白名单校验。

客户端只发送现有严格载荷：

```json
{
  "action": "set_member | set_filter | revoke_filter",
  "confirmed": true,
  "reason": "规范化后的 3–500 字原因"
}
```

服务端继续校验请求来源、内容类型和大小、UUID、动作枚举、明确确认与原因长度，再通过既有 entitlement 服务完成事务和审计。此改动不增加批量操作、管理员互授、管理员创建或任何用户站入口。

## 组件边界

- `AdminShell`：只负责管理员身份、管理端导航和响应式布局。
- `AdminUsersPage`：解析 Tab、列表查询和所选审计账号，加载服务端数据并组合页面。
- `AdminUserEntitlementControl`：管理理由、禁用说明、确认和单次提交。
- 纯展示/状态辅助函数：计算规范化理由状态、动作可用性和禁用原因，供组件与针对性测试共同使用。

不抽象账户页壳层，不修改用户端导航结构，不做无关样式重构。

## 测试与验证

实现采用红—绿—重构：

1. 先补失败测试，证明空理由和短理由会给出可理解的就地提示，合法理由会开放适用动作，当前权益不适用的动作有独立说明。
2. 补失败测试，证明确认框重述目标、动作、规范化原因，并构造现有严格 API 载荷。
3. 补页面级测试，证明独立壳包含管理员身份与两个管理 Tab，管理端仍不出现在用户站导航。
4. 保留并运行管理员列表、权益变更和审计 API 的未登录、非管理员、非法请求及成功路径测试。
5. 使用隔离的本地数据库和管理员会话，验证浏览器提交经过真实 Next.js API 后，权益实时变化且产生审计记录。
6. 在桌面和移动视口检查身份区域、Tab、表格滚动、理由提示、确认框和反馈。
7. 运行针对性测试、Web TypeScript 检查和 Web 生产构建。

## 非目标

- 全局跨用户审计列表或新的审计查询协议。
- 批量权益修改。
- 页面内授予管理员权限。
- 将管理端加入站点导航、账户页或站内跳转链路。
- 重构正式站账户设置壳层。
